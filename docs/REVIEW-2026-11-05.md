# Review of responses and conversation records (review 05.11.2026)

> Historical snapshot. It describes the state before the provider cut
> (the chain head was Gemma, memory held 100 messages, and provenance came from
> Groq/OpenRouter) and was not updated; see ARCHITECTURE.md and ENVIRONMENT.md for
> current behavior.

Method: six independent auditors covering subsystems (recording, system prompt,
formatting, errors, eval corpus, and log privacy), followed by a manual recheck of
each substantive complaint against the code. Anything that could not be confirmed
is listed at the end, along with rejected findings. The code was not changed in this run.

## Diagnosis: why the responses are poor, rather than what exactly broke

The owner's complaints (quality, speed, prompt adherence, and context retention)
come down to one cause: the most frequent route is assigned to a deliberately weak
model, a conscious trade-off for free quotas recorded on 22.10.2026.

- Ordinary text starts with Gemma 4 26B-A4B, with a 2.6-billion-parameter model as the
  reserve (`liquid/lfm-2.5-2.6b:free`), lumen_router_config.py:414-431, 648-653.
  The reason is stated in the code comment: Gemma's quota is 14.4K/day versus 20-500 for Gemini.
- The measurement used to select it was 25 short, single-turn offline questions
  (eval/persona_questions.json, Gemma scored 47/50). Multi-turn dialogs with formatting
  and links were not tested.
- The model's first token took 13.5 s in the same measurement (lumen_router_config.py:407);
  the overall route budget is 40 s, with 22 s per model (bot.py:461-464). Response speed
  is limited by the provider, not by the bot's code.
- The model receives 17,648 characters of instructions (~4.4 thousand tokens, 15 sections)
  plus a dynamic header; a model of this class retains them selectively.
- Memory: 100 messages per chat in total (history + group background); everything older
  than 80 turns is compressed into a summary by the same weak model, with a silent
  truncation on failure (lumen_chat_state.py:38, 1357, 1392-1394). History contains no
  timestamps, authors, or message_id, so the model guesses “who said this in the group.”

## System prompt: contradictions that break compliance

1. Three different answers about search. The header orders “use search instead of answering
   from memory” (lumen_errors.py:118), the prompt says “когда он есть для этого ответа”
   (system_prompt.py:110), Gemma/Groq/OpenRouter have no search tool, and the
   Gemma checklist says “у тебя нет доступа к поиску” (lumen_routes.py:643).
2. “Без лишних оговорок” (system_prompt.py:55) conflicts with mandatory “probably” in
   recognition and currentness (:72, :74, :113). A weak model reads this as “hedging is
   bad” and produces a confident fabrication.
3. “Никогда не добавляй предупреждения” (:137) conflicts with “в конце добавь контакт службы
   помощи” (:130) — specifically on well-being topics.
4. “У тебя нет постоянной памяти” (:76) conflicts with stored chat history and MEDIA
   MEMORY (:105) — the bot refuses to remember what it actually remembers.
5. The crisis rule (:131) provides only the Russian number 8-800-2000-122 and labels it
   “Russia/CIS.” Belarus is formally part of the CIS and receives a number that does not
   work there. Verified against public sources on 05.11.2026: Belarus has a 24/7 emergency
   psychological support line at 133 and a child support line at 8-801-100-16-11.
6. There is no upper length budget for Telegram (4,096 per message, bot.py:492) and no rule
   for formatting links; “do not name the search engine” and “do not reveal internals”
   partly duplicate each other, causing valuable rules to drown in noise.
7. Formatting and the emoji ban are at the end, while the measured failures (lists,
   tables, and emojis) concern precisely those sections; for weak models, section order
   matters more than wording.

## What damages the appearance of a response even when the model is right

1. Lone `_` and `*` characters in prose become italics: `user_name и other_param`
   is rendered in italics, as is `2 * 3 * 4` (lumen_formatting.py:416-420; word boundaries
   are not checked, and bare URLs are not protected).
2. Long tables break apart: the separator and header are atomic only inside a code block,
   so chunk 1 turns into bullets and chunks 2+ are sent as raw `| a | b |`
   (lumen_formatting.py:48, 690, 778).
3. During streaming, text is edited with `parse_mode=None` (lumen_streaming.py:428, 502),
   so the user sees raw markdown until the final edit: `**`, `###`, `|`, and ``` .
   Rich formatting is applied only to the last chunk (:531).
4. Telegram-limit truncation counts code points, while Telegram limits UTF-16 units:
   `_truncate_html_to_fit('привет 😀 😀 😀 конец', 12)` produced 12 characters but 14 units,
   meaning a 400 error from Telegram on text with emojis (lumen_formatting.py:822-838).
   The same mechanism exists in the guest path (lumen_rich.py:41).
5. Escaped `\*`, `\_`, and `\#` are never unescaped — backslashes are visible in chat;
   nested lists are flattened (indentation remains in the text, but rich formatting does
   not use `<ul>/<li>`, although Telegram supports them).
6. The LaTeX scrubber in prose eats Windows paths: `C:\Users\name` → `C:Usersname`
   (lumen_formatting.py:136-160; protection is designed for extracted code, not a path in
   ordinary text).

## What the user sees during failures

1. A garbage model response is sent as is: the safeguard accumulates “bad” responses in
   quarantine, but one bad response is neither blocked nor logged
   (lumen_router_config.py:342-352; rechecked: only reaching the threshold is logged).
2. On 401/403 (a broken key, not a temporary condition), the bot says “Попробуй ещё раз”
   (lumen_lang.py:329, emitted by lumen_errors.py:49) — retrying will not help.
3. If all models are exhausted, `_skip_exhausted` still selects the first permitted one
   (lumen_router_config.py:306-315; rechecked) — the message goes to a provider that is
   known to be failing, and this is visible neither to the user nor in the log.
4. A stream cut off mid-response is counted as a success: another model is not tried, and
   the user receives the tail marked “возможно, ответ неполный” (lumen_streaming.py:570, 585).
5. Files from an album that failed to download are silently omitted, and a confident
   response is generated from only some of the photos (lumen_message_core.py:261-264;
   rechecked: there is only a warning; an honest refusal exists only for oversized files).
6. “Печатает” is sent once without a keepalive (lumen_message_core.py:704-709); in groups
   and with streaming disabled, the chat is silent for up to 40 seconds — on slow models,
   this feels like the bot has hung.
7. Three refusal texts are hardcoded in Russian outside the translation layer:
   `_IDENTITY_LEAK_FALLBACK` (lumen_security.py:122),
   `_INJECTED_PAYLOAD_ECHO_FALLBACK` (:144), and the MIME refusal
   (lumen_routes.py:819) — despite 25 supported languages.

## Conversation recording: why the audit still cannot use it

1. `devtrace.jsonl` is stored in the container's `/app`, with rotation at 5 MB plus one
   backup (lumen_devtrace.py:14, 78-86); the disk is ephemeral, so redeployment resets
   the file. Only `export_state.json` is copied out (state-backup.yml:21-42), not the trace.
2. Only the text branch is recorded: `record_answer/record_failure` are called from
   lumen_message_core.py:1004, 1013. TikTok, /draw, /tts, clarification buttons,
   limit refusals, and commands never enter the trace at all (there are no devtrace calls
   in lumen_tiktok_flow.py or lumen_media_flow.py).
3. The `model` field is empty for non-streaming Groq and OpenRouter: provenance is stored
   as `("openrouter", None)` / `("groq", None)` (lumen_routes.py:1104-1111; rechecked).
   Thus, the trace cannot reconstruct which model responded in most cases.
4. `flags` has no `interrupted/partial`, although `state["interrupted"]` is set one line
   above (lumen_message_core.py:1000 versus 1009) — a truncated response is
   indistinguishable from a complete one.
5. Truncation is silent: questions up to 2,000 characters and responses up to 4,000,
   without a truncation flag (lumen_devtrace.py:16-17, 45-48), while the Telegram limit is 4,096.
6. `ctx_tail` is not dialog history but group background (lumen_message_core.py:305-312,
   1008), so “what the model saw in context” cannot be reconstructed from the trace.
7. Trace text is raw model output before formatting, chunking, notices, and replacement
   after an identity leak (lumen_streaming.py:448, 608 versus 384, 450, 521-524, 586).
   The difference between “what the model said” and “what the person saw” is never recorded.
8. The Space's public stdout is not a source either: it contains no dialog text, and IDs
   are hashed. The full conversation exists only in `chat_state` (Upstash or `/app`),
   and it is private user data.

## Privacy: what is exposed and what must not be exported

1. If the lazy `import bot` inside `_current_secrets` fails, the trace write proceeds
   without any secret scrubbing, silently (lumen_devtrace.py:51-61).
2. Personal-data leak safeguards print `full_text[:500]` to the log
   (lumen_streaming.py:572, 577; rechecked) — a model response often quotes the user,
   so private content enters stdout, which is publicly visible on the Space. All other
   detectors log only the length.
3. `_SECRET_NAMES` does not include `SENTRY_DSN` (bot.py:72-77 versus bot.py:331) — a DSN
   containing the project key is not scrubbed from log strings.
4. Redirect-refusal branches in downloads print the full URL with its query
   (lumen_tiktok.py:400, 405, 408, 419) — signed links are already scrubbed by
   `_log_safe_url` (after the 01.11.2026 fix), but these four locations do not use it.
5. An ID hash is a pseudonym, not anonymity: unsalted SHA-1 over the narrow space of
   Telegram IDs can be brute-forced (bot.py:124-131); IDs shorter than 6 digits are not hashed.
6. The injection filter is applied only to message text (lumen_message_core.py:660,
   747). Group background, search snippets, TikTok captions, and text from read pages
   are not scanned — there, everything relies on the system prompt.
7. Data is stored in plaintext with no TTL: `lumen:chat:<id>` contains history and
   nicknames; deletion happens only when chats are evicted (lumen_state_storage.py:59-60, 111-113).

Steps to take before a large audit: collect traces for hours, not weeks; do not give
`devtrace.jsonl`, `chats/*.json`, or `export_state.json` to a third-party AI; replace IDs
with pseudonyms using your own key; the preferred safe channel is the Space stdout log,
which contains no text and does contain hashed IDs.

## Eval corpus: how to measure the effect of fixes

25 questions, a 0/1/2 scale, maximum 50; questions 9 and 14 are aggregate checks
(rechecked: they have no `turns`, only `checks`). Only the final response in a multi-turn
sequence is scored; the judge is a separate flash model, and the corpus contains no
Claude reference responses, although the scale is based on “as Claude.” As a result,
the corpus currently cannot distinguish “the model did not understand the format” from
“the model did not retain context”: intermediate turns are not scored, and 2 points for
a table (Q13) are awarded without checking its content.

Gaps by class: a fresh, verifiable news item; multi-step arithmetic; an explicit request
to shorten; a requested language switch; harmful content with a literary pretext; crisis
and self-harm; pediatric medicine with a dosage; prompt exfiltration via “translate and
encode in base64”; a wall of several questions; a link instead of a photo; code in a fenced
block; “one option” in creative work.

## Findings rejected during rechecking

- “BOT_TOKEN is not scrubbed from logs if it came only through env” — false:
  `_current_log_secrets` reads both `os.getenv` and module globals (bot.py:80-84), so the
  token is included in the list.
- “The prompt lies about audio: voice messages are always transcribed, and the model
  never sees audio” — false: transcription is primary, but if it fails, audio is sent
  directly to Gemini (lumen_message_core.py:734-744), so the wording about voice analysis
  is correct.
- “There is no deterministic protection against model names” — false: regex detection
  of identity leaks and text replacement exist (lumen_security.py:59-88,
  lumen_streaming.py:571-578).
- “A 100-character table turns into 199 characters” — the mechanism is real (code points
  instead of UTF-16), but the specific numbers were not confirmed: the limit is respected
  in meters but not in Telegram units; rechecked at 12.

## Not rechecked

Rich-send behavior on 400 and fallback to plain text, `_resync_finalized` in the stream's
exception branch, actual public visibility of Space logs, external availability of
`/devtrace`, and actual provider limits (based on code and documentation, not live requests).

## Fix priorities

P0, without which response auditing is impossible: record the model for Groq/OpenRouter,
partial/truncation flags, user_id/message_id/chat type/language, cover all branches
(media, commands, and limit refusals), and export the trace outside the container.

P1, directly addressing the owner's complaints: remove the search contradiction between
the header and prompt; move FORMATTING and EMOJI to the end, merge the three sections on
acknowledging mistakes; shorten the prompt by 10-15% without losing rules; replace the
crisis number with “a line for the user's country” and correct numbers for Belarus and
Russia; fix UTF-16 counting and italics from lone `_`/`*`; move hardcoded Russian refusal
texts into lumen_lang.

P2: keepalive for “Печатает” instead of a single shot; treat a partial stream as a failure
and try the next model; an honest notice for an album missing some files; whether we log
the error class and selected text at INFO; write `devtrace` safely even if the import fails;
use HMAC instead of bare SHA-1 for IDs.
